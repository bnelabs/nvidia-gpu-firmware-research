# Prior Art — Public Reverse Engineering & Security Research on NVIDIA GPU Firmware

*Research notes for the owner of the lab rig studying their own hardware. Compiled 2026-10-15; all links checked that date. Framing: analysis of one's own cards, no offensive tooling, no techniques aimed at systems you don't own.*

## TL;DR

- envytools (Marcin Kościelnicki et al., since ~2010) is the foundational public RE corpus for NVIDIA GPUs: Falcon ISA disassembler (`envydis`), `rules-ng-ng` register database, vBIOS decoders — much of it still the only documentation for on-die microcontrollers.
- Martin Peres's PhD (LaBRI Bordeaux) produced the first systematic RE of NVIDIA **PMU firmware** (OSPERT '13), proving the falcon-based power microcontroller could be driven from an open driver.
- NVIDIA itself has since published the biggest "prior art": `open-gpu-doc` (register/class manuals incl. **BIOS-Information-Table, DCB, Devinit, Falcon-Security**) and the `open-gpu-kernel-modules` (MIT/GPLv2, since 2022), which define the entire GSP RPC control plane.
- GSP firmware (`gsp.bin`) ships as a signed ~15 MB RISC-V **ELF** and has been redistributed in linux-firmware since Nov 2023; public analysis is still thin — mostly architectural descriptions, not RE write-ups.
- The LHR saga (2021–22) showed NVIDIA's consumer anti-mining "protection" was **driver heuristics + vBIOS/SKU identity + silicon counters**, without cryptographic enforcement; it was fully unlocked by miners and then quietly removed by NVIDIA in driver 522.25 (2022-10-12).
- The strongest modern GPU-firmware security talk is 39C3 (Dec 2025): Elise Amber Katze broke the **NVIDIA Tegra X2 secure bootchain** (USB bootloader exploit → fault injection → BootROM dump → unpatchable BootROM vulnerability).
- GPU security research 2023–2026 is dominated by side-channel and memory-disclosure work (LeftoverLocals, GPU.zip) and GPU-TEE surveys — almost nothing targets the **dGPU firmware** layer, which is a genuine gap.
- For AMD context: Rudolf Marek's 31C3 SMU firmware analysis (2014) and the BC-250 community's live SMU firmware RE are the closest analogues to what this repo wants for NVIDIA.
- **Correction to earlier repo notes:** "Breaking Band" (33c3-adjacent memory) is Comsecuris's *cellular baseband* RE talk (REcon 2016, Nico Golde & Dániel Komaromy) — not AMD PMU firmware. Cite 31C3/Rudolf Marek for AMD PMU instead.
- Remaining unexplored: GSP ELF internals, GSP RPC fuzzing, Ada/Blackwell vBIOS BIT-table diffs, falcon secure-boot/auth on consumer cards, GOP/UEFI driver extraction.

## 1. The envytools / nouveau lineage (2001 → today)

**What it is.** nouveau is the community driver built by clean-room reverse engineering of NVIDIA hardware since ~2003. Its documentation hub is the [NvHardwareDocs page](https://nouveau.freedesktop.org/NvHardwareDocs.html) on nouveau.freedesktop.org, which points at "envytools: THE repository of reverse engineered documentation and RE tools".

**envytools.** The [envytools repository](https://github.com/envytools/envytools/) contains: `docs` (plain-text RE documentation; HTML mirror at [envytools.readthedocs.io](https://envytools.readthedocs.io/en/latest/index.html)), `envydis` (disassembler/assembler for NVIDIA ISAs), `rnn`/`rnndb` (the `rules-ng-ng` XML register database), `nvbios` (vBIOS decoders, see §6), and `nva` (raw MMIO access tools). The documentation is primarily the work of **Marcin Kościelnicki** — his CV states: "since Jun 2011 – envytools docs: Reverse-engineered hardware documentation for nVidia GPUs, *mostly covering firmware-running microprocessors*" ([CV PDF](https://0x04.net/~mwk/cv.pdf)). Several forks exist (e.g. [lynxeye-dev/envytools](https://github.com/lynxeye-dev/envytools)) and parts were upstreamed to the nouveau tree ([SourceForge mirror](https://sourceforge.net/p/nouveau/envytools/ci/master/tree/)).

**The falcon microcontroller.** envytools documents the [falcon microprocessor](https://envytools.readthedocs.io/en/latest/hw/falcon/index.html) — the small 32-bit RISC-ish controller (a "Fast Logic CONtroller") instantiated across NVIDIA GPUs as PMU, SEC, secboot, PDAEMON, NVDEC/NVENC front-ends, etc. It covers the ISA, interrupts, code/data DMA, crypto coprocessor, and debug interfaces. This is the direct ancestor of today's **NV-RISCV / GSP** architecture, per the [Open-IOV GPU Firmware page](https://open-iov.org/index.php/GPU_Firmware) ("Falcon / NV-RISCV processors run the NvOS... GSP is an embedded controller used for offload of the RM Core").

**Martin Peres's PMU work.** The canonical publication is [*Reverse engineering power management on NVIDIA GPUs*](http://phd.mupuf.org/files/ospert13.pdf) (OSPERT 2013, slides [here](https://publications.mupuf.org/files/ospert13_slides.pdf)), part of Peres's PhD at LaBRI ([publication list](https://phd.mupuf.org/publication/categories/nouveau/)). It documented voltage regulators, temperature sensing, clock scaling and the PMU falcon firmware protocols well enough to implement dynamic power management in nouveau — and framed RE as a response to vendors not shipping autonomic-friendly interfaces.

**What it achieved:** a complete-enough register/ISA/firmware protocol picture for Kepler–Pascal era cards; the falcon ISA disassembler still used today; the template (RE → rnndb → driver) that open kernel modules later made partially obsolete. **Unexplored leftovers:** PMU/secboot microcode for GA10x and later is still not publicly documented in envytools depth; falcon debug/JTAG posture on consumer cards was never published.

## 2. The official documentation era (2018 → 2026)

- **open-gpu-doc.** NVIDIA's [open-gpu-doc repository](https://github.com/NVIDIA/open-gpu-doc) (moved from download.nvidia.com, actively updated — last push 2026-06) publishes register/class manuals for pascal/turing/ampere/volta plus directory-level docs for **[BIOS-Information-Table](https://github.com/NVIDIA/open-gpu-doc)**, `DCB` (display config), `Devinit` (init sequences) and notably a **`Falcon-Security`** document. This is *vendor*-published ground truth — a huge inversion of the old RE dynamic.
- **Open kernel modules.** Since May 2022, [open-gpu-kernel-modules](https://github.com/NVIDIA/open-gpu-kernel-modules) publishes the kernel-side of the driver under a dual MIT/GPLv2 license (see [COPYING](https://raw.githubusercontent.com/NVIDIA/open-gpu-kernel-modules/main/COPYING)). Crucially for us, its README documents the `nouveau/` helper that extracts GSP firmware from the source tree, and points to `nouveau_firmware_layout.ods` describing the firmware file layout. The GSP-RM architecture (CPU-RM vs GSP-RM split) is summarized in the [TI linux-firmware WHENCE entry](https://git.ti.com/cgit/processor-firmware/ti-linux-firmware/commit/WHENCE?h=ti-linux-firmware&id=f4a3c72e5c413a601d1e21f9606f1c94a610d05d) and the [Open-IOV GSP and GSP-RM page](https://open-iov.org/index.php/GSP_and_GSP-RM).
- **GSP firmware distribution.** NVIDIA relicensed the GSP binaries to permit redistribution in May 2023 (R535 beta) — see [Phoronix, "NVIDIA Cleans Up GSP Firmware Binary License"](https://www.phoronix.com/news/NVIDIA-GSP-Firmware-License) — and pushed 62 MB of GSP blobs into linux-firmware.git in Nov 2023 ([Phoronix](https://www.phoronix.com/news/NVIDIA-Big-GSP-Firmware-Dump)). The firmware is "two signed binary images per GPU family, verified by the GSP hardware before execution" per the [linux-graphics-stack-book ch. 9](https://github.com/jreuben11/linux-graphics-stack-book/blob/main/chapters/part-03-nouveau-story/ch09-gsp-rm-firmware.md).
- **GSP firmware internals (community).** The deepest public analysis found so far is architectural: [DeepWiki's GSP Firmware Internals for the rtx-p2p project](https://deepwiki.com/kacper-daftcode/rtx-p2p/3-gsp-firmware-internals) describes `gsp_elf_9.bin` as a ~15 MB ELF executed by the RISC-V core with a global config structure in BSS. There is **no published symbolicated RE write-up** of GSP-RM internals we could find.
- **Developer talks.** Verified: Karol Herbst's [FOSDEM 2020 "Nouveau Status update"](https://archive.fosdem.org/2020/schedule/event/nouveau/) (Brussels, K.4.401, 2020-02-01); Faith Ekstrand & Karol Herbst, ["Nouveau/NVK update", XDC 2023](https://www.youtube.com/watch?v=SwBe7l9tqro) (YouTube) covering kernel GSP support; and the ongoing **nova** Rust driver whose 2025 patch series processes the [GSP bootloader](https://lore.freedesktop.org/nouveau/20250822-nova_firmware-v1-4-ff5633679460@nvidia.com/) ([v3 series](https://lore.freedesktop.org/nouveau/20250902-nova_firmware-v3-8-56854d9c5398@nvidia.com/)). Earlier GSP-era context: NVIDIA's own [GSP Firmware chapter](https://download.nvidia.com/XFree86/Linux-x86_64/510.39.01/README/gsp.html) (510.39.01, 2022) documents the initial opt-in GSP mode. Karol Herbst later [stepped down as nouveau maintainer](https://www.phoronix.com/news/Karol-Herbst-Nouveau-No) (2024), which matters for community continuity. [VERIFY: whether Herbst gave a FOSDEM 2022–2025 talk specifically on GSP; the 2020 talk predates GSP support.]

## 3. The LHR (Lite Hash Rate) saga, 2021–2022

**Timeline (verified sources):**
- Feb 2021: RTX 3060 ships with an anti-mining limiter; within weeks NVIDIA's own **developer driver 466.11 accidentally removed it**, and NVIDIA admitted the mistake to The Verge ([Ars Technica, Mar 2021](https://arstechnica.com/tech-policy/2021/03/nvidia-accidentally-releases-driver-to-un-nerf-cryptocurrency-mining/); [Tom's Hardware](https://www.tomshardware.com/news/nvidia-admits-it-hacked-its-own-rtx-3060-crypto-limiter)).
- May 2021: LHR v2 rolls out with RTX 3080 Ti and new 3070/3060 Ti batches (~50% Ethash cut); LHR v3 appears later on RTX 3050 / 3080 12GB ([cool-mining overview](https://cool-mining.org/en/mining-en/nvidia-gpu-mining-en/lhr-graphics-cards-hashrate-limitation-and-workarounds/)).
- 2021–22: partial bypasses reached ~70–90% (NBMiner "LHR mode"; lolMiner 1.50 full unlock for v1/v2 paired to specific drivers 510.x/512.x; early drivers ≤460.39 lacked detection) — see [hashrate.no LHR tracker](https://www.hashrate.no/c/NVIDIAs_LHR) and the [TechSpot report on NiceHash's full bypass](https://www.techspot.com/news/94504-nvidia-lhr-limiter-has-bypassed-enabling-full-mining.html).
- Community vBIOS editors automated the hardware-side: e.g. [NvidiaRTX-LHRv2Unlocker](https://github.com/liji3278/NvidiaRTX-LHRv2Unlocker) ("BIOS modifier for RTX cards with LHR v2 lock") and similar tools that read, patch and reflash the card's ROM ([ExtremeTech coverage of the software+vBIOS unlock](https://www.extremetech.com/computing/331965-software-utility-and-bios-reportedly-unlock-full-mining-capabilities-on-nvidia-gpus)).
- End state: NVIDIA **removed the limiter in driver 522.25** (release date 2022-10-12, [NVIDIA download page](https://www.nvidia.com/Download/driverResults.aspx/193713/en-us/), noted by [NiceHash support](https://www.nicehash.com/support/mining-help/nicehash-miner/how-to-enable-nbminer-lhr-unlock-in-nicehash-miner) and [crypto-mining.blog](https://crypto-mining.blog/en/mining/nvidia-removed-the-lhr-lock-in-the-latest-522-25-driver/)) after Ethereum's move to PoS.

**What it revealed about the protection design** (owner-hardware analysis): per the cool-mining/Dell-community synthesis, "the limitation is implemented in the drivers and VBIOS, but some of the logic has been moved to the die itself" — i.e., the limiter was (1) Ethash/dagger-hashimoto **detection heuristics in the driver**, which then throttles memory clocks/voltage; (2) an **LHR identity** carried by the vBIOS/SKU so tools and drivers could recognize a limited card (which is exactly why vBIOS patching was a viable unlock path); (3) some measurement logic in silicon, making it harder than a pure software switch. Notably: no cryptographic attestation, no GSP involvement (Ampere GSP was optional then), and enforcement lived in a *user-replaceable* driver. The saga is the best public case study of how NVIDIA implements and ships a consumer-side "feature restriction" spanning vBIOS + driver + silicon — and how brittle such designs are when the enforcement point is user-controlled. *[VERIFY: exact silicon-level mechanism (fuse vs. PMC counter) was never published; treat "moved to the die" as secondary-source claims.]*

## 4. GPU security talks & research, 2016 → 2026

- **39C3, Dec 2025 — "Making the Magic Leap past NVIDIA's secure bootchain and breaking some Tesla Autopilots along the way"**, Elise Amber Katze ([event page](https://events.ccc.de/congress/2025/hub/event/detail/making-the-magic-leap-past-nvidia-s-secure-bootchain-and-breaking-some-tesla-autopilots-along-the-way); [video](https://media.ccc.de/v/39c3-making-the-magic-leap-past-nvidia-s-secure-bootchain-and-breaking-some-tesla-autopilots-along-the-way)). Tegra X2 secure boot fully broken: bootloader USB exploit, fault injection to dump the BootROM, and an unpatchable BootROM vulnerability. Not a GeForce dGPU talk, but the deepest public defeat of an NVIDIA secure-boot chain, with methodology (fault injection, BootROM dumping) directly relevant to our falcon/GSP questions.
- **33C3, Dec 2016 — "Console Hacking 2016"** (marcan et al., [media.ccc.de](https://media.ccc.de/v/33c3-7946-console_hacking_2016)): PS4 AMD-APU hardware/firmware bring-up from a security perspective; good comparative material.
- **LeftoverLocals** (Trail of Bits, Jan 2024; CVE-2023-4969): listening to LLM responses through leaked GPU local memory on Apple/Qualcomm/**AMD** GPUs ([project page](https://leftoverlocals.com/), [paper](https://arxiv.org/html/2401.16603v1), [AMD-SB-6010](https://www.amd.com/en/resources/product-security/bulletin/amd-sb-6010.html)). NVIDIA GPUs were reported *not* affected — a useful reminder that attack surface is vendor-specific.
- **GPU.zip** (IEEE S&P 2024): data-dependent GPU compression side channel enabling cross-origin pixel stealing; vendors incl. NVIDIA initially declined to fix ([paper](https://www.hertzbleed.com/gpu.zip/GPU-zip.pdf)).
- **GPU TEE survey (2024–2025):** [*Confidential Computing on Heterogeneous CPU-GPU Systems*](https://arxiv.org/abs/2408.11601) (ACM) maps the emerging attack surfaces of GPU confidential-computing stacks — the best current survey lens on why firmware matters.
- **CVE flow & disclosure:** NVIDIA vulnerabilities are tracked continuously (e.g. [OpenCVE vendor feed](https://app.opencve.io/cve/?vendor=nvidia)); from **Oct 1, 2026** NVIDIA PSIRT publishes bulletins only on GitHub in Markdown/CSAF/CVE format ([NVIDIA/product-security](https://github.com/NVIDIA/product-security)).
- *[VERIFY: DEF CON 32 (2024)/33 (2025) GPU-firmware-specific talks — the archives ([dc-32](https://defcon.org/html/links/dc-archives/dc-32-archive.html), [dc-33 schedule](https://defcon.org/html/defcon-33/dc-33-schedule.html)) skew toward AI/ML security; no dedicated dGPU-firmware talk identified yet.]*

## 5. AMD comparisons (for context)

- **31C3 (Dec 2014), "AMD x86 SMU firmware analysis"**, Rudolf Marek ([video page](https://media.ccc.de/v/31c3_-_6103_-_en_-_saal_2_-_201412272145_-_amd_x86_smu_firmware_analysis_-_rudolf_marek)): architecture, security, and vulnerabilities of the AMD System Management Unit firmware — the direct AMD analogue of NVIDIA's PMU/GSP story. **This, not "Breaking Band", is the correct citation for AMD PMU firmware RE.**
- **"Breaking Band"** — Comsecuris (Nico Golde, Dániel Komaromy), REcon 2016: reverse engineering and exploiting the Shannon *cellular baseband* ([slides](https://comsecuris.com/slides/recon2016-breaking_band.pdf), [talk page](https://www.recon.cx/2016/talks/Breaking-Band.html)). Included here to correct the record: it is baseband firmware RE, not GPU PMU; its methodology (large-scale decompilation of a monolithic firmware blob) transfers well to `gsp.bin`.
- **BC-250 community SMU RE (2023–2026):** repurposed PS5-derived boards (Cyan Skillfish) got a live RE effort on AMD's SMU firmware with a message-ID map ([bc250-collective/amd_smu_reverse_engineering](https://github.com/bc250-collective/amd_smu_reverse_engineering), [community guide](https://github.com/katzzero/bc250-unofficial-community-guide)) and tooling ([marenz2569/amd-smu-rev-tools](https://github.com/marenz2569/amd-smu-rev-tools)). This is the modern template for "community RE of vendor power-management firmware on owned hardware". Reference architectures: [DeepWiki on AMD PSP](https://deepwiki.com/amd/firmware_binaries/2-platform-security-processor-(psp)) and [SMU/PMFW](https://deepwiki.com/amd/firmware_binaries/3.1-smu-power-management).

## 6. vBIOS table reverse engineering (published)

- **envytools nvbios**: decode of the bit/BIT-structured card description tables (init scripts, DCB, perf tables) — see the [nvbios overview](https://deepwiki.com/freedreno-zz/envytools/4-nvidia-vbios-parsing-(nvbios)) and the nouveau wiki's [DumpingVideoBios](https://nouveau.freedesktop.org/DumpingVideoBios.html) (dump methods incl. `nvagetbios`).
- **Ilia Mirkin's standalone [NVIDIA VBIOS Parser](https://people.freedesktop.org/~imirkin/nvbios/)** — web-renderable table dumps.
- **Vendor docs**: open-gpu-doc's `BIOS-Information-Table`, `DCB`, `Devinit` and `virtual-p-state-table` directories are NVIDIA's own spec for parts of what community tools parsed ([repo](https://github.com/NVIDIA/open-gpu-doc), HTML mirror [nvidia.github.io/open-gpu-doc](https://nvidia.github.io/open-gpu-doc/)).
- **Community tooling lineage**: Kepler BIOS Tweaker ([TechPowerUp](https://www.techpowerup.com/download/kepler-bios-tweaker/)), Maxwell BIOS Tweaker, and modern editors; TechPowerUp's vBIOS database is the de-facto reference corpus for known-good ROMs. *[VERIFY: Ada/Blackwell-era table structures are not covered by any public parser we found — open-gpu-doc documents the new-style tables but no community editor exists.]*

## Unexplored angles

Gaps where new research adds value (all feasible on owned, expendable hardware):

1. **GSP ELF forensics.** `gsp*.bin` is a plain ELF; nobody has published a symbol/layout map of GSP-RM (string tables, RTOS identity, RPC handler tables). A static + dynamic (VM test bench) analysis would be first-of-its-kind public work.
2. **GSP RPC surface mapping.** The control calls are defined in open kernel module headers but undocumented as an API; diffing them across driver versions (e.g. 615.71.09 vs 615.78.08) would show the true "firmware ABI" churn rate.
3. **Falcon/GSP secure boot on GeForce.** Who signs GSP and falcon microcode, what the bootloader verifies, and whether signed-downgrade windows exist on consumer cards — partially answered for Tegra by the 39C3 talk, untouched for dGPUs.
4. **Ada/Blackwell vBIOS BIT structures.** No public parser covers the new table layouts; a diff-based decoder (known-good ROMs from TechPowerUp + open-gpu-doc specs) is open territory.
5. **GOP/UEFI x64 driver inside vBIOS** — extraction and analysis of the display driver module (a separate signed binary embedded in the ROM).
6. **LHR silicon counter forensics** — the exact on-die measurement mechanism was never published; a Turing/Ampere-era card on a test bench could answer it definitively.
7. **Falcon microcode for GA10x+** (PMU, SEC2, secboot) — envytools-grade documentation ends around Pascal; everything Ampere-onwards is dark.
8. **PSIRT-informed fuzzing** of the RM/GSP ioctl surface in VFIO-isolated VMs (responsible disclosure path documented in legal-and-safety.md).
